# Logging and anomalies

[← Back to Architecture overview](../ARCHITECTURE.md)

The library uses the standard `[LoggerMessage]` source-generated logging pattern throughout, with hard-coded `EventId`/`EventName` pairs drawn from one flat, project-wide catalog (`HealthCheckPlusEventIds`), not a per-class numbering (so renaming a method never changes what shows up in logs, and two classes logging through the same category can never collide on the same id). Beyond the routine begin/end/error logs around check and publisher execution, there is a specific family of Warning-level logs for **defensive paths that were handled without failing the caller** — most are paired with a `healthcheckplus.anomalies` metric (see [Metrics](../ARCHITECTURE.md#metrics)); each exception to that is called out below, with why:

- `HealthCheckPublisherCycleError` — a publisher failed this cycle; the loop is continuing.
- `HealthCheckPlusBackGroundPublishReportBuildError` — building the report to hand to publishers this cycle failed (most likely `Predicate` throwing); no publishers were invoked this cycle, and the loop is continuing.
- `HealthCheckDisposeError` — an adopted check's `Dispose()` threw; the remaining checks are still being disposed.
- `HealthCheckPlusUpdateDropped` — `Update()`'s result was dropped (unregistered key, or an overlapping execution already claimed `Running`).
- `HealthCheckPlusSwitchToDropped` — `SwithState` (behind `SwitchToUnhealthy`/`SwitchToDegraded`) dropped a manual override because a scheduled execution was already `Running` for that check; the override never applied, and the in-flight execution's own result will land shortly instead. Paired with the `switchto_dropped_while_running` anomaly.
- `HealthCheckExecutionAborted` — a scheduled check never actually completed because the ambient cancellation fired (an HTTP client disconnected, or a background-cycle Timeout elapsed) while it was still running — not the check itself failing. Its last known result (`LastResult`, `Duration`, `Origin`) is left untouched rather than overwritten with a synthetic one; only the scheduling state (`Running`, `DateRef`) is released, advancing `DateRef` to the abort time so it's retried on its normal schedule instead of hot-looping. This means `DateRef` can briefly read newer than the `LastResult`/`Duration`/`Origin` it's paired with in a report — see the `dateRef` caveat in `RUNBOOK.md`.
- `HealthCheckPlusMetricsRecordingError` (in `CacheHealthCheckPlus`) / its two per-class siblings — recording a metric itself failed. **Not** paired with an anomaly metric: if the `Meter`'s own recording is what's broken, calling back into it to report that would be circular and could throw again for the same reason. This one stays log-only, by design.
- `HealthCheckPlusBackGroundStopCancellationError` — `_stopping.Cancel()` itself threw during shutdown (e.g. a health check's own `CancellationToken.Register` callback misbehaving). **Not** paired with an anomaly metric: shutdown is already underway by the time this fires, the same reason the shutdown-cancellation case in `RunPublisherAsync` (see [Publishing](./publishing.md)) records nothing at all - unlike that case, this one still logs rather than staying fully silent, since swallowing it with zero signal would violate this same class's own doctrine for exactly this kind of catch.
- `HealthCheckPlusBackGroundLoopFaulted` (Critical, not Warning, and not paired with an anomaly metric) — the background loop's own top-level task ended up faulted, meaning something escaped every one of the try/catch blocks above. `StopAsync`'s continuation observes this explicitly; without it, a fault here used to dispose the task and vanish with zero signal, indistinguishable from a graceful shutdown. It is the one signal that distinguishes "the loop ran and then died" from "the loop never started" - see `docs/RUNBOOK.md`'s diagnosis for a background service that seems to have stopped entirely. A throwing `ILogger` sink used to be exactly this kind of escape (fixed by the `SafeLog` guard described below); this log exists as the backstop for whatever the next one turns out to be.

The reverse pairing also exists, deliberately: `healthcheckplus.anomalies` with reason `logging_sink_failed` has **no** matching log. Nearly every `Log.*`/`ILogger` call across `CacheHealthCheckPlus`, `DefaultHealthCheckServicePlus`, and `HealthCheckPlusBackGroundService` goes through that class's own private `SafeLog` helper (the log-side mirror of the metrics-side `SafeRecordMetric`) instead of being called directly - a throwing `ILogger` sink (a broken third-party logging provider) must never be able to kill the background loop, break `Dispose`/`DisposeAsync`/`StopAsync` (none of which may throw), turn an already-successful check evaluation into a 500 on `/health`, or replace a real exception with the sink's own. `SafeLog`'s catch records `logging_sink_failed` instead of trying to log the logging failure - the same circularity risk `SafeRecordMetric`'s own catch already avoids, mirrored. If this counter is climbing, look at the registered `ILoggerProvider`(s), not at HealthCheckPlus itself.

**Point of attention**: one call is a knowing exception to "nearly every" above - `DefaultHealthCheckServicePlus.RunCheckAsync`'s `_logger.BeginScope(...)`. It opens an `IDisposable` inside a `using` statement, which can't be wrapped in `SafeLog` the same way a plain `void`-returning log call can (there is no `IDisposable` to hand back through a guarded lambda). A throwing `BeginScope` still faults that check's own execution and surfaces as a real exception rather than a recorded `logging_sink_failed` anomaly. See [`POINTS_OF_ATTENTION.md`](../POINTS_OF_ATTENTION.md#known-accepted-edge-cases) for what this means in practice.

**Point of attention**: the guarantee `SafeLog` provides has one more accepted gap, by explicit decision, not yet closed: `SafeLog`'s own catch calls `RecordAnomaly` unguarded (see `SafeRecordMetric`'s note above about why metrics recording is itself safe to call from here) - if the `ILogger` sink AND the `Meter`/`MeterListener` both fail at the same moment, that second failure can still propagate out of `Dispose`/`DisposeAsync`/`StopAsync`'s continuation. Kept as a documented, accepted limitation rather than adding a third channel (e.g. writing to `Console.Error`) to close it - see [`POINTS_OF_ATTENTION.md`](../POINTS_OF_ATTENTION.md#known-accepted-edge-cases).

None of the defensive paths listed above are silent. A defensive `try/catch` that swallows an exception with no log and no metric — even a "best-effort, the outer log already covers it" one — is treated as a defect in this codebase, not a stylistic choice, with one deliberate category of exception: an `OperationCanceledException` that is itself just the app shutting down, not a real failure (the same carve-out already noted for `RunPublisherAsync`'s shutdown-time cancellation). `HealthCheckPlusBackGroundService`'s initial startup delay (`CheckHealthAsync`) swallows exactly that case with no log and no metric, on purpose - there is nothing an operator would act on by seeing "the process was asked to stop" logged once per shutdown.
