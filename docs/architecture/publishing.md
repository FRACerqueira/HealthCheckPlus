# Publishing

[← Back to Architecture overview](../ARCHITECTURE.md)

When `AddBackgroundPolicy` is used, `HealthCheckPlusBackGroundService` removes the native `HealthCheckPublisherHostedService` (so publishers aren't driven twice) and drives every registered `IHealthCheckPublisher` itself, after each polling cycle, subject to two extra filters (`PublishingOptions`). **Point of attention**: `PublishingOptions.Enabled` defaults to `false` - see [`POINTS_OF_ATTENTION.md`](../POINTS_OF_ATTENTION.md#publishing-results) for what this means in practice.

**Point of attention**: the native-service removal happens once, on `IServiceCollection`, at the moment `AddBackgroundPolicy` is called - it is order-dependent. If anything calls `IServiceCollection.AddHealthChecks()` again afterward (typically the app's own startup code - a real `AspNetCore.HealthChecks.*`-style third-party extension does not, since it operates on the `IHealthChecksBuilder` it's handed rather than re-calling `AddHealthChecks()`, confirmed empirically), .NET's `TryAddEnumerable` silently re-adds the native service, since nothing of that type is registered at that later point anymore. Left undetected this produced one of two silent bad outcomes whenever at least one `IHealthCheckPublisher` was registered, independent of `Publishing.Enabled` (that option only governs whether `HealthCheckPlusBackGroundService` itself drives publishers, not whether the native one does): the native service driving publishers on its own schedule, bypassing `AfterIdleCount`/`WhenReportChange`/`PublisherCondition` entirely, or both it and this service driving them, duplicating every dispatch - with zero log or metric signal either way. `HealthCheckPlusBackGroundService.StartAsync` now checks for the native service's presence and throws `InvalidOperationException` immediately if found - but only when a publisher is actually registered, since a resurrected native service with nothing to invoke is harmless and failing the whole host over it would be a false positive for a background-polling-only setup (the default shape, since `Publishing.Enabled` defaults to `false`). See [`POINTS_OF_ATTENTION.md`](../POINTS_OF_ATTENTION.md#setting-it-up) for the one-line rule this protects against.

- **`AfterIdleCount`** — only publish every N idle cycles, not every cycle.
- **`WhenReportChange`** — only publish if the aggregate report actually changed since the last publish (compared via the actual `{name+status}` pairs, `BuildReportKey` - previously a 32-bit hash of them, replaced after a ninth audit round noted a hash collision would permanently suppress a real, unpublished change with no signal). The last-published key is a single value shared by every publisher, only updated after a cycle's publisher dispatch completes without throwing — so if one publisher is permanently broken (always throws), the key never updates, and *every* publisher (including ones that succeeded) is re-dispatched the same unchanged report every `AfterIdleCount` cycles instead of just the broken one. See [`POINTS_OF_ATTENTION.md`](../POINTS_OF_ATTENTION.md#publishing-results) for why this is intentional, not a bug.
- A publisher can additionally implement `IHealthCheckPlusPublisher.PublisherCondition` for its own custom gating.

Each publisher invocation is fault-isolated (`RunPublisherAsync`): a publisher that throws is logged and recorded with `healthcheckplus.publisher.invocations{healthcheckplus.publisher.result=error}`, then the exception is rethrown so the *cycle* (not the whole background loop) sees it. `PublisherCondition` is evaluated inside this same try/catch, so a throwing condition is attributed to that exact publisher (naming it in `HealthCheckPublisherError` and tagging the `error` metric with its type) instead of only surfacing one level up, as the generic cycle-dispatch failure below with no indication of which publisher or why. The cycle-level dispatch (`await Task.WhenAll(tasks)` over all publishers) is itself wrapped in a try/catch that logs `HealthCheckPublisherCycleError` (Warning) and records a `publisher_cycle_failed_but_continued` anomaly. **Point of attention**: without this outer try/catch, a single publisher throwing once would permanently kill the entire background loop (checks *and* publishing) for the rest of the process's life, with no crash and no log — a scenario a happy-path publisher test won't catch, so a publisher that's expected to occasionally throw is worth testing explicitly against this exact behavior.

Building the report handed to that dispatch (`BuildReportForPublishing`) is wrapped in its own, separate try/catch that logs `HealthCheckPlusBackGroundPublishReportBuildError` (Error) and records a `publish_report_build_failed` anomaly. **Point of attention**: this exists for the same reason as the dispatch try/catch above it, at a step that used to have no guard at all — a `Predicate` that throws (e.g. assuming every registration carries a tag it doesn't) used to kill the entire background loop exactly like an unguarded publisher would, just one step earlier in the cycle.

`BuildReportForPublishing` excludes two kinds of cache entry from what gets hashed (`WhenReportChange`) and handed to publishers: one the consumer-supplied `HealthCheckPlusBackGroundOptions.Predicate` excludes from running here, and — separately — one that simply hasn't run even once yet (`Origin != HealthCheckTrigger.None`). Both are decided by `CacheHealthCheckPlus.CreateReport(Func<string, bool> includeName)` from the same `Snapshot` read used to build each entry's data - not two separate calls at two different times, which used to let a check that completed its first real run in the gap between them be included while still carrying its `InitCache` seed data. **Point of attention**: `InitCache` seeds every check as `Healthy`/`Origin=None` before it first runs, and a plain `CreateReport()` has no way to tell that seed apart from a genuine result — a check whose own `Delay` (`AddCheckPlus`/`AddCheckLinkTo`) outlives the background service's `Delay`+`Idle` (the README's own example values, 30s vs. 5s, trigger this on the very first cycle) would otherwise be published as a real Healthy observation before it was ever actually checked.
