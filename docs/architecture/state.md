# State: `CacheHealthCheckPlus` and `ItemCacheHealth`

[← Back to Architecture overview](../ARCHITECTURE.md)

`CacheHealthCheckPlus` holds one `ItemCacheHealth` per registered check name (`Name`, `LastResult`, `DateRef`, `Duration`, `Origin`, `Running`), seeded by `InitCache` at startup with `HealthStatus.Healthy`. It implements the public `IStateHealthChecksPlus` interface, which is how application code reads cached status directly (`Status()`, `StatusResult()`, `TryGetUnhealthy()`, etc.) or forces a manual override (`SwitchToUnhealthy`/`SwitchToDegraded`, backed by `SwithState`).

This cache — along with `HealthChecksPlusRegistrationState` (registration-time flags and adopted-check instances) — is scoped per `IServiceCollection`, not process-wide. **Benefit**: multiple hosts built in the same process (`WebApplicationFactory`-style integration tests, .NET Aspire, parallel test runs) each get fully isolated health-check state; a check registered in one host can never leak its cached status, or its adopted external check instance, into another. **Point of attention**: this is why there's no global accessor - see [`POINTS_OF_ATTENTION.md`](../POINTS_OF_ATTENTION.md#reading-and-reacting-to-status) for what that means for code that needs to read this state.

`Update(key, trigger, result, lastExecute, duration)` is the single point every execution path — foreground, background, and the manual `SwitchTo` override — converges on to write a new result. Two things worth knowing about it:

- It **drops** the update (logging a Warning, `HealthCheckPlusUpdateDropped`, and recording a `healthcheckplus.anomalies` metric with reason `update_result_dropped`) if the key isn't registered, or if `Running` isn't already `true` for it. The latter is reachable under the same overlapping-execution scenario `TryBeginRun` (see [Scheduling](./scheduling.md)) guards against at the *scheduling* stage — this is the *safety net* if two runs somehow still overlap (e.g. a manually-triggered check racing a scheduled one).
- Metric recording (`RecordStatusTransition`/`RecordCheckExecution`) is wrapped in its own try/catch (`SafeRecordMetric`), because a `MeterListener` callback (e.g. a third-party OTel exporter with a bug) runs synchronously on the calling thread — an uncaught throw there would otherwise propagate out of `Update()` and, on the HTTP path, turn an instrumentation failure into a 500 response. **Metrics must never be able to break health evaluation.**

`HealthCheckTrigger.SwitchTo` (the manual override) is recorded as a status transition but deliberately excluded from `RecordCheckExecution`/duration metrics — no code actually ran, so it isn't an "execution."

`SwithState` also calls `UpdateStatusName()` right after `Update()`, so a named aggregate registered via `AddStatusName` (read back through `Status(name)`) reflects a manual override immediately. **Point of attention**: `Status(null)` (the default, unnamed aggregate) always recomputes live and never needed this — only a *named* aggregate is cached in `_statusName`, refreshed by every foreground request and every background cycle that has a due registration to run, *and* now by every manual override too, so it can never go stale waiting for the next poll where something was actually due. **Point of attention**: `CheckHealthPlusAsync` now calls `UpdateStatusName()` before rethrowing a batch failure (e.g. the caller disconnecting mid-request), not after - so a named aggregate still reflects every result that did commit via `Update()` even on a request that ultimately surfaces as faulted. `BackGroudCheckHealthPlusAsync` already ordered its own equivalent rethrow this way; this closes the asymmetry between the two paths.

**Point of attention**: because `SwithState` calls `UpdateStatusName()`, a `StatusHealthReport` delegate that itself calls `SwitchToUnhealthy`/`SwitchToDegraded` (directly, or indirectly through its own code) recurses straight back into `UpdateStatusName()` - and again, and again, since the same delegate runs every cycle - which would otherwise end in an uncatchable `StackOverflowException` with no log or metric to explain it. `UpdateStatusName()` detects this same-thread reentrancy (a `[ThreadStatic]` flag, not a lock - two independent top-level calls on different threads, e.g. an HTTP request racing a background cycle, are unaffected) and throws a clear `InvalidOperationException` instead. See [`POINTS_OF_ATTENTION.md`](../POINTS_OF_ATTENTION.md#reading-and-reacting-to-status) for the plain-language rule this protects.

**Point of attention**: a named aggregate's report is scoped to the same checks its own `HealthCheckPlusOptions.Predicate` (if any) would let through — `UseHealthChecksPlus(path, options)` calls `AddStatusName(options, includeName)` with `includeName` translated from that same `Predicate` against the real `HealthCheckRegistration` list (a translation `CacheHealthCheckPlus` can't do itself, since it only ever tracks check names). `UpdateStatusName()`/`Status(name)` build that name's report from `includeName`, not the full cache — including for the default aggregate (`StatusHealthReport` omitted), which now takes `includeName` into its own live `_statusDeps` read instead of ignoring it. Confirmed this used to diverge: `HealthCheckMiddlewarePlus` evaluates `StatusHealthReport` against the `Predicate`-filtered report it builds for its own HTTP response, but `UpdateStatusName()` always fed every registered name's delegate the same full, unfiltered cache regardless of any `Predicate` — a `Predicate`-scoped endpoint and `Status(name)` for that same registered name could report different statuses for what was meant to be the identical check set.

**Point of attention**: even with `Entries`/`Status` now equivalent between the two paths, `HealthReport.TotalDuration` is not, and this is not a bug to fix - it's a genuine semantic difference between what each path's report represents. The HTTP endpoint's own report carries `totalTime.Elapsed`, the real wall-clock time spent running that request's batch of due checks. Every report `BuildReport` produces (`CreateReport()`, `UpdateStatusName()`, `Status(name)`'s cold path) carries `TimeSpan.Zero` instead, because there is no batch execution to time - it's an instantaneous read of already-computed cached results. Neither a synthesized pseudo-duration for the cache-read paths nor zeroing it out on the endpoint path would actually fix this: the two numbers measure different things, and forcing them to match would mean fabricating one of them. See [`POINTS_OF_ATTENTION.md`](../POINTS_OF_ATTENTION.md#reading-and-reacting-to-status) for what this means for a `StatusHealthReport` delegate.

**Point of attention**: `UpdateStatusName()`/`Status(name)`'s lazy-compute path are the only two writers of `_statusName`, and both invoke a consumer-supplied `StatusHealthReport` delegate that can be arbitrarily slow - two concurrent calls (e.g. a routine cycle and an override's own call) can therefore finish in either order regardless of which one started first or captured the fresher report. A plain `_statusName[key] = status` write used to let a slower call, working from an older report, silently overwrite a faster call's fresher result. Each write is now tagged with `_stateVersion` (a counter incremented once per real state change, inside `Update()`), and only applied if it isn't older than whatever is already stored (`TryStoreStatusName`). The version and the report it tags are captured together, under `_lock` (the same lock `Update()` also takes around its own state change), *before* the delegate runs - never as two separate, unsynchronized reads. An earlier version of this fix read the version just before calling `CreateReport()`, with neither step synchronized against a concurrent `Update()`; that closed the original override-reverting scenario above but left a narrower residual where two callers' version reads could tie while a concurrent `Update()` landed mid-way through one of their report builds, so a tied version - which `TryStoreStatusName`'s `>` comparison doesn't reject - could still pair with divergent report content. The consumer delegate itself still runs outside the lock, so a slow `StatusHealthReport` never stalls scheduling or any other cache access.
