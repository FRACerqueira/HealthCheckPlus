# Changelog

All notable changes to HealthCheckPlus are documented here.

## V4.0.0

- **Breaking**: `AddHealthChecksPlus()` no longer takes a `names` parameter. The set of tracked health checks is now taken directly from whatever ends up registered via `AddCheckPlus`/`AddCheckLinkTo`/any native `IHealthChecksBuilder` extension - there is no separate list to keep in sync, and no way for it to drift from the real registrations.
- Fixed the Degraded status policy being ignored when resolving the next check interval on HTTP health check requests.
- **Breaking**: health checks registered without an associated policy now fail fast at startup with a clear error naming the check, instead of a delayed runtime exception. An app on a prior version that ran fine on 3.0.1 with such a check will now refuse to start until a Healthy policy (`AddCheckPlus`/`AddCheckLinkTo`) is added for it.
- Health check state is now isolated per host, so multiple hosts running in the same process (integration tests, .NET Aspire) no longer share cached results.
- Added native metrics instrumentation (`System.Diagnostics.Metrics`) for check executions, status transitions, and publisher invocations — no new package dependency.
- The background service now keeps running checks and publishing even if a publisher throws, including if the configured `Predicate` itself throws while building the report to hand to publishers (logged as `HealthCheckPlusBackGroundPublishReportBuildError`, recorded as a `publish_report_build_failed` anomaly).
- Fixed `SwitchToUnhealthy`/`SwitchToDegraded` not refreshing a named status aggregate (`Status(name)`, registered via `AddStatusName`) - a manual override could go unreflected in that aggregate until the next request or background cycle happened to run.
- Fixed the main `HealthCheckPlus` NuGet package embedding a private copy of `HealthCheckPlus.Abstractions.dll` while declaring no dependency on the `HealthCheckPlus.Abstractions` package - installing both (as recommended for projects that only need the abstractions) could load two independent copies of the same types. The main package now declares a normal package dependency instead.
- Fixed a cached check result's `Status`/`Description`/`Duration`/`Origin` being torn under concurrent updates - a reader could observe a mix of an old and a new result (e.g. a new `Status` paired with the previous `Description`). These now live in one immutable snapshot swapped atomically, and every "Plus" response writer now serializes a frozen copy instead of the live cache entry.
- All scheduling now compares against UTC time, avoiding drift on non-UTC hosts.
- A throwing `IHealthCheckPlusPublisher.PublisherCondition` is now attributed to that exact publisher (`HealthCheckPublisherError`, and the `error` result on `healthcheckplus.publisher.invocations`) instead of only surfacing as the generic cycle-level failure with no indication of which publisher or why.
- **Breaking**: `AddUnhealthyPolicy`/`AddDegradedPolicy`/`AddCheckPlus`/`AddCheckLinkTo` now fail fast at startup if a policy names a health check that was never actually registered (a typo), instead of silently registering a policy that could never match any real check. An app on a prior version that relied on this going unnoticed will now refuse to start until the name is fixed or the policy removed.
- Fixed `PublishingOptions.Enabled`'s XML doc, which claimed a setter that doesn't exist and the wrong default for how it's actually configured via `AddBackgroundPolicy`.
- A health check that hasn't run even once yet is no longer published as a genuine Healthy result by the background service - it's excluded from what gets hashed (`WhenReportChange`) and handed to publishers until it actually runs, the same way a `Predicate`-excluded check already was.
- Fixed `AddCheckPlus`/`AddCheckLinkTo`'s `delay`/`period` XML docs, which incorrectly described `IHealthCheckPublisher` timing instead of the check's own scheduling.
- `SwitchToUnhealthy`/`SwitchToDegraded` no longer drop a manual override silently when the check is currently running - it's now logged (`HealthCheckPlusSwitchToDropped`) and recorded as a `switchto_dropped_while_running` anomaly.
- Policy lookup (`AddUnhealthyPolicy`/`AddDegradedPolicy`/`AddCheckPlus`/`AddCheckLinkTo`, and the startup validations that check them) now compares check names case-insensitively, matching how the rest of the library already treats them - a policy could previously go unmatched against its own check over a casing difference alone.
- `IStateHealthChecksPlus`'s XML docs now document the `ArgumentException`s its members can throw for an unregistered name.
- `IStateHealthChecksPlus.ConvertToPlus` is now evaluated eagerly instead of lazily, so a failure (an entry naming a check no longer tracked) surfaces immediately rather than mid-write of an already-started JSON response.
- Internal casts that assume a native `HealthCheckService`/`IStateHealthChecksPlus` registration is actually the concrete type `AddHealthChecksPlus()` registers now fail with a clear message naming the registration and the actual type found, instead of a generic `InvalidCastException`, if something replaced or decorated that registration.
- Policy lookup (resolving which `HealthCheckPlusPolicyStatus` applies to a check) is now O(1) instead of a linear scan through every registered policy - the per-cycle/per-request cost of resolving policies for every registration was effectively quadratic in the number of checks, now linear.
- Fixed a data race in releasing a check after an ambiently-cancelled execution: it used to clear the `Running` flag and only then rewrite the cached result, with neither step synchronized against a concurrent scheduling decision for the same check - now both happen atomically under the same lock already used to make scheduling decisions atomic.
- `HealthCheckPlusBackGroundOptions.Delay` now rejects negative values (previously only rejected `Timeout.InfiniteTimeSpan`), matching every other `TimeSpan` option in the class. A negative `Delay` used to be accepted silently and only fail later, when the background loop's own startup delay threw and killed the loop with no log or metric.
- Fixed a scheduling race where two concurrent callers for the same check (e.g. an HTTP request and a background cycle) could both read "not running, due" before either marked it running, both schedule the same check, and run it twice concurrently - with whichever finished second having its result silently dropped. Checking due-ness and marking the check running now happen as one atomic operation.
- An ambiently-cancelled execution (an HTTP client disconnecting, or a background cycle's own `Timeout` firing) now advances the check's schedule as if the attempt had happened, so it's retried on its normal per-status period instead of immediately on every subsequent poll or request with no backoff at all.
- `HealthCheckPlusBackGroundOptions.Timeout` now also bounds dispatching a cycle's publishers, not just running that cycle's due checks - a publisher with no timeout of its own (e.g. an HTTP call to an endpoint that never responds) used to be able to block the entire background loop indefinitely, checks included.
- The background service's `WhenReportChange` hash is now only committed once publisher dispatch has actually succeeded. Committing it unconditionally used to mark a failed dispatch's status as "already published", causing the next cycle to skip retrying the notification for that status change until it changed again.
- Fixed `HealthCheckPlusOptions.WriteShortDetails`'s response `Content-Type` having drifted to a bare `application/json`, inconsistent with every other response writer's `application/json; charset=utf-8`.
- `AddUnhealthyPolicy`/`AddDegradedPolicy`/`AddCheckPlus`/`AddCheckLinkTo` now reject a `null`/empty check name immediately with a clear `ArgumentException`, instead of a confusing `NullReferenceException` later (from startup validation, for the first two) or immediately (from `AddCheckLinkTo`'s own name comparison).
- **Breaking**: `AddBackgroundPolicy` now fails fast with `InvalidOperationException` if called more than once for the same `IServiceCollection`, instead of silently registering a second, independent instance of the background service - two concurrent loops each executing checks and dispatching publishers on their own schedule, with nothing indicating the mistake. A consumer that happened to call it twice (e.g. from two separate startup extensions) and relied on that silently working will now see this throw at startup.
- `IStateHealthChecksPlus.Status()`/`AddStatusName`'s default aggregate no longer throws `InvalidOperationException` when zero health checks are registered - it now returns `Healthy` (matching the native `HealthReport.Status`'s own default for zero entries), and `LastReport()` returns `null` instead of throwing.
- The background service no longer publishes a phantom `Healthy` result for a check whose very first real run completes in the narrow window between building the report and deciding which checks are eligible to publish - both are now decided from the same read of the check's cached state instead of two separate reads at two different times.
- `StopAsync` now logs (`HealthCheckPlusBackGroundLoopFaulted`, Critical) if the background loop's task ever ends up faulted, instead of silently disposing it with no signal at all that something escaped every other guard.
- Fixed several internal `EventId` collisions in the background service's logging, where unrelated log events (a publisher timeout and a publisher error; a publisher cycle error and the background loop's own cancellation-error log; a publisher metrics-recording error and the report-build error log; the background cycle's own unhandled-exception log and a publisher error; a publisher timeout and the background loop's own processing-timeout warning log) shared the same numeric id, making them indistinguishable when filtering logs by id alone.
- `InternalCast.To<T>` now gives its clear error message for a `null` value too, instead of an unrelated `NullReferenceException`.
- Fixed a check being marked permanently `Running` (never scheduled again, on either path, until the process restarts) if a call between that marking and the point that normally releases it threw - most concretely, if the injected `ILogger` itself threw (a broken logging provider/sink) while logging that a batch of checks was starting.
- Fixed a race where a named status aggregate (`Status(name)`, registered via `AddStatusName`) could briefly revert a fresh manual override back to a stale value: two concurrent calls to compute that aggregate (e.g. one from a routine cycle, one triggered by the override itself) could write in either order regardless of which one captured the more recent data, so a slower call working from an older snapshot could overwrite a faster call's fresher result. Each computation is now tagged with a version and a write is only applied if it isn't older than what's already stored.
- **Breaking**: all internal log `EventId` numbers are now assigned from one project-wide catalog instead of one independent, restarting-from-100 range per class - closes the collision class described above for good, at the cost of most log entries' numeric id changing (the `EventName` string every entry is actually identified by is unchanged). A consumer filtering or alerting on a specific numeric `EventId` (rather than its `EventName`) will need to update those filters.
- `StopAsync`'s shutdown continuation no longer runs on whatever `TaskScheduler` happens to be ambient at the point it's called - it now always uses the thread pool, so a custom, limited-concurrency scheduler saturated with unrelated work can no longer stall shutdown for a reason unconnected to this class's own logic.
- Hardened two places against a theoretical rather than demonstrated risk: `SwithState` now reads a check's last result once and reuses it, instead of two separate reads that could in principle observe different generations; the named-status-aggregate function table (`AddStatusName`) is now a `ConcurrentDictionary`, matching every other piece of shared state in the same class, instead of a plain `Dictionary` whose thread-safety depended on an unenforced startup-ordering assumption.
- Fixed a check being left permanently `Running` if applying one item's result in a batch threw - most concretely, if the injected `ILogger` itself threw while logging that an item's execution was aborted by ambient cancellation. That one item's failure used to abort the whole batch, leaving every later item in it stuck `Running` too, not just the one that failed; each item's release is now isolated, and any failures are collected and rethrown together as an `AggregateException` once the whole batch has been finalized (previously, a single item's own exception propagated directly).
- `AddUnhealthyPolicy`/`AddDegradedPolicy`/`AddCheckPlus`/`AddCheckLinkTo`'s XML docs now document the `InvalidOperationException` they throw when `AddHealthChecksPlus` wasn't called first - already documented for `AddBackgroundPolicy`, but missed for these four.
- Fixed a narrow residual race where a named status aggregate (`Status(name)`) could still be computed from a version and a report captured as two separate, unsynchronized steps - a concurrent write landing in between could tie with the version already read, defeating the version check meant to reject stale writes. The version and the report are now captured together, under the same lock used elsewhere for atomic state changes.
- Fixed a check-execution batch's own cancellation/timeout exception being silently replaced by a second, independent failure while applying that batch's results (e.g. a throwing `ILogger` sink on one item) - both exceptions now surface together as an `AggregateException` instead of one masking the other, and the original exception's stack trace is preserved when only it fails.
- The background service's `_stopping` cancellation source is now disposed when the service itself is (it already implements the pattern every other disposable singleton this library registers uses) - previously leaked for the lifetime of its `IServiceCollection`, most visible when creating and disposing many hosts in the same process (integration tests, .NET Aspire).
- `AddBackgroundPolicy`'s XML doc now says its "called twice" exception is scoped to the same `IServiceCollection` (matching the actual guard), not `IHealthChecksBuilder`, and its default-values list now includes `Idle = 1 second`.
- `UseHealthChecksPlus`'s four overloads now document every exception they can throw (`ArgumentNullException`, and - for the two `HealthCheckPlusOptions` overloads - `ArgumentException`/`InvalidOperationException`), and `AddHealthChecksPlus`/`AddUnhealthyPolicy`/`AddDegradedPolicy`/`AddCheckPlus`/`AddCheckLinkTo`/`AddBackgroundPolicy` now document the `ArgumentNullException` they throw for a `null` builder/collection - both previously undocumented. Also fixed a malformed XML doc comment on two `UseHealthChecksPlus` overloads that dropped the first sentence of their `<remarks>` from the generated docs entirely.
- See [`docs/ARCHITECTURE.md`](./docs/ARCHITECTURE.md) and [`docs/RUNBOOK.md`](./docs/RUNBOOK.md) for the full design and operational reference.
